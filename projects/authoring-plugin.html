Help-Content Authoring Plugin

Turning one-off article fixes into reviewed, repeatable workflows a whole writing team can run in plain English

Client: Intuit Customer Success (TurboTax, Credit Karma, ProTax) Year: 2026 Deliverables: Claude Code plugin (18 skills), edit pipeline, safety model, bulk-edit and scheduled automations, writer onboarding guides

Overview

Intuit's help content lives in a knowledge base of more than 20,000 articles, notices, and reusable content blocks across TurboTax, Credit Karma, and the professional tax products. Writers maintained it one article at a time, by hand, in a CMS editor that was never built for bulk work.

I designed and built the plugin that changed that. Writers now ask Claude for what they need in plain English: "work this Jira ticket," "replace this phrase in every ProSeries article that mentions it," "add this screenshot to step 3." The plugin finds the articles, makes the change, checks it against brand and house standards, saves it as a Draft, proves the change landed, and shows a before/after table. Nothing publishes until a writer says yes.

I'm a content designer, not an engineer. Nobody assigned this. I saw how much of the team's time went into mechanical edits, built the fix, and kept building until the whole team could use it.

The Problem

Most help-content work isn't writing. It's maintenance: a product name changes, a tax law changes, a link breaks, an SME files a ticket asking for a sentence to be fixed in a dozen places. Each of those meant opening the CMS, finding every affected article, editing each one, and checking each one. A single edit took 3–5 minutes. A sweep across a product line took days, and things got missed. One sweep I ran later found a live article still describing a tax credit phase-out that had been repealed in 2022.

The CMS had no safe way to do this at scale, and the people who owned it were rightly cautious about anyone writing to production in bulk. So the real problem was two problems: make editing fast enough to matter, and make it safe enough that the platform team, my managers, and the writers themselves would trust it.

How It Got Here

This didn't ship in one piece. It moved through five phases in about seven months, and each one was shaped by a constraint I didn't control.

Phase 1 — A direct API integration (March–June). I connected Claude Code to the CMS's REST API, so Claude could read, search, and edit articles, with a human review on every write. An average edit dropped from 3–5 minutes to about 30 seconds, and batches ran 10+ articles a minute with verification. I agreed a governance model with the CMS's engineering team: Draft-only writes, manual publish, named operators, capped batches, and an edit-lock check before every write. I proved the lock check in testing with a second operator. Claude detected that a colleague had the article open, named them, and refused to write.

Phase 2 — Shaping the official tool (June–July). Engineering's target state was their own AI connection to the CMS, delivered through an internal interface. Rather than fight that, I made sure nothing would be lost in the move. I wrote a prioritized capability inventory of everything my integration could do that the new tool needed on day one, plus a test plan with ground-truth match counts so incomplete search results would show up as a measurable gap.

Phase 3 — Going direct (July–August). Instead of waiting on the interface, I connected Claude Code straight to the same MCP server underneath it. I worked through the authentication chain and a few platform bugs, took production live, and confirmed in a pilot that the team's existing access was already enough. No new permissions request needed.

Phase 4 — A plugin for the team (September). I packaged my personal skills into a self-updating plugin, so a fix reached every teammate on their next run. I replaced an 8-step manual edit flow with a single command, ran a UAT with three writers, and shipped their fixes within days.

Phase 5 — The registry and a hard cutoff (September–October). When we learned the direct connection would end on October 31, I moved the plugin to Intuit's new desktop access layer within a day, verified it on Mac and Windows, and folded the whole thing into Intuit's internal plugin registry as the Customer Success track of a shared plugin. One install, one place to fix things, and no writer left on a credential that stops working.

How an Edit Works

Every change runs through the same pipeline, whether a writer asked for one word or a hundred articles:

  • Start. Resolve the article from any link a writer pastes, fetch the current Draft, and check whether someone else is editing it.
  • Edit. Make the change, then run a brand, house-style, and AI-readiness review over the whole article, fixing clear-cut issues in the same Draft.
  • Check. Run mechanical standards checks: heading levels, sentence case, link formats, alt text, banners instead of bold notes, and more.
  • Ship. Rebuild the payload from a fresh fetch, save the Draft with an author note, then re-read both the Draft and the live version to prove the change landed. If anyone changed the article in the meantime, it stops.
  • Publish. Only after the writer says yes.
  • Report. Every run ends with one table: ticket → article → before/after, plus anything still blocked. After publish, the SME gets a plain-language note with the customer-facing link and the ticket is closed.

Designing the Safety Model

The most important design work on this project wasn't the interface. It was deciding where a human has to say yes, and where they shouldn't have to.

Early versions stopped constantly for approvals that protected nothing, and writers stopped trusting the prompts because there were too many of them. So I designed it around one human gate: publishing, archiving, and multi-article bulk writes stop for a yes. Everything else runs. Drafts, receipts, and rollback are the safety net.

  • Every Draft and publish is recorded under the writer's own name. No shared credentials.
  • Writes only go through the pipeline, never a raw update call, because the protection is in the payload the pipeline builds and verifies.
  • Image uploads ride on the article's publish approval, because they're a public write.
  • If a call is denied, the plugin never retries through a different tool. A security review treats that as evasion, and so do I.
  • Failures report privately to the writer, not in team channels.

Getting a human-in-the-loop system right is a content design problem: what the person is asked, when, and how often. Ask too much and the approvals become noise. Ask too little and nobody trusts the system.

Bulk Edits and Automations

Once single edits were reliable, scale was the point. A writer can hand the plugin a CSV of changes, including find-and-replace across articles, several edits to one article, tag and SEO changes, or bulk creation of new articles. It runs the whole batch without stopping on a bad row, then produces a receipt for review. A tax-law workflow takes structured work orders from another team's impact analysis and lands one Draft per affected article.

Some articles don't need a writer at all. The Delayed Acknowledgments article, which tells accountants which state e-file acknowledgments are running late, now rebuilds and publishes itself from the source data every day, with an hourly check that keeps known-issue banners current. New issues are only ever proposed, never auto-published, and a cloud backup posts the update to the team even when my laptop is off.

Making It Usable for Non-technical Writers

My teammates are writers, not developers, and the first time some of them saw raw terminal output it alarmed them. So a lot of the work went into the experience around the tool:

  • A non-technical onboarding wizard and an interactive setup guide, including a tab that explains why the tool exists and what it changes.
  • Plain-language sign-in repair. When authentication fails, the plugin prints click-by-click steps a writer can follow, and retries known transient failures itself instead of blaming the user.
  • A Chrome extension that adds an "Open in Editor" button to any help article, so writers can jump from the public page to the right place to edit it.
  • A routing hook so plain requests like "execute this Jira" reach the plugin even when a writer doesn't name it. I added it after a teammate's request never triggered the plugin at all.

Impact

  • 20,700+ help articles, notices, and reusable blocks reachable by the tooling across Intuit's consumer, small-business, and professional tax help
  • A single edit cut from 3–5 minutes by hand to about 30 seconds; an 8-step manual flow replaced with one command
  • Writers on Mac and Windows editing production safely with no credentials of their own beyond their normal sign-in
  • The team moved off a retiring access path before a hard October 31 cutoff
  • Adopted as the Customer Success track of a shared plugin in Intuit's internal plugin registry, backed by an automated self-test suite
  • 149+ articles updated through the plugin in its first week of team use (a verified minimum, before content refresh season began)
  • An estimated ~1,060 hours a year saved on the team's top content refresh use cases, based on teammates' task estimates from prior years
  • Team Rockstar award, August 2026

What This Demonstrates

Content design at scale is increasingly about the systems behind the words: how content gets changed, who checks it, and what keeps it accurate after it ships. This project is that, end to end. The skills are written instructions. The standards checks encode the style guide. The approval model is a decision about what a person is asked and when.

It's also how I like to work. Every phase of this hit a wall I didn't control: access was revoked, the official tool wasn't ready, a connection was being retired. Each time, the answer was to keep the work moving and bring the right people along, not to wait.

I didn't build a tool for myself. I built the way my team edits content.
